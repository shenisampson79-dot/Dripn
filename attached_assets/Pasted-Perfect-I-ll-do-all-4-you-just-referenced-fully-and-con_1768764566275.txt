# 1️⃣ BACKEND STATES FOR “SECOND OPINION”

Think of this as a **state machine**, not a feature.

---

## Core entities

### `SecondOpinionRequest`

```
id
user_id (nullable pre-signup)
outfit_id
urgency_level (normal / urgent)
status (pending / partial / complete / expired)
created_at
```

---

### `Vote`

```
id
request_id
voter_id
vote (approve / unsure / change)
reason_chip (optional)
created_at
```

---

## State progression

### STATE 1 — `pending`

* Request created
* No votes yet
* Stylist already gave its recommendation

Stylist copy:

> “I’ve shared this for a second opinion. I’ll update you.”

---

### STATE 2 — `partial`

Triggered when:

* ≥ **3 votes** OR
* ≥ **10 minutes** (urgent) OR
* ≥ **30 minutes** (normal)

Stylist copy:

> “Early reactions are coming in…”

This is important psychologically — users feel movement.

---

### STATE 3 — `complete`

Triggered when:

* Vote threshold reached (see section 2)
* OR time cap reached

Stylist summarizes results.

---

### STATE 4 — `expired`

If:

* User never signs up
* App closed for >24h
* No notification permission

Data retained, but results gated behind signup.

# 2️⃣ HOW MANY VOTES ARE “ENOUGH”

This is NOT a popularity contest — it’s a **confidence signal**.

---

## MVP thresholds (deliberately low)

### Normal (pre-signup, no urgency)

* **5–7 votes total**
* Time cap: 60 minutes

### Urgent (post-signup)

* **3–5 votes**
* Time cap: 10–15 minutes

Why this works:

* Humans don’t need 100 opinions
* Early consensus matters more than volume
* Lower thresholds reduce operational pressure

---

## Consensus logic (not raw counts)

You do **not** show:

* “4 vs 3”
* Percentages
* Charts

You show **interpretation**.

Internal logic:

* ≥60% “approve” → positive consensus
* ≥40% “change” → stylist adjusts
* High “unsure” → stylist reframes confidence

---

## Stylist always speaks last

Example output:

> “Most people agree this works. A few felt it leans formal — I’d still wear it, but you could soften it with trainers.”

This preserves authority.

# 3️⃣ FAILURE CASES & GRACEFUL HANDLING

This is where trust is won or lost.

---

## Case A — No votes come in

This *will* happen early.

Stylist response:

> “I didn’t get enough responses this time — I’d stick with my original recommendation.”

Important:

* No apology spiral
* No blame
* AI stays confident

---

## Case B — Split votes (no clear consensus)

Stylist response:

> “Opinion is split — which usually means this comes down to personal preference. I’d go with the original look.”

This reinforces decisiveness.

---

## Case C — Community disagrees strongly with AI

Only allowed in **social-risk contexts**.

Stylist response:

> “I’d normally stand by this, but given the setting, I’d adjust slightly.”

Then adjust one element, not the whole outfit.

---

## Case D — Low-quality or troll votes (post-MVP)

Handled silently by:

* Voter reputation
* Activity recency
* Simple rate limits

Never expose this to users.
